# T001: 统一可解释性 API 设计

**所属 Paper**: 🟢 Explainable_FD_Toolkit
**分类**: API 设计
**优先级**: P0
**依赖**: 无

---

## 背景

### 现状描述
- 当前主仓库各模型的可解释性输出格式不统一
- 需要设计统一的 `explain()` 接口

### 为什么需要合并
- 所有 UXFD 方法需要统一的可解释性接口
- 便于 post-run 检查和 LLM 层消费

### 当前问题
- 接口规范未定义
- 返回格式（JSON schema）未确定

---

## 合并任务分解

### 子任务 1: 设计 `explain()` 接口规范
- [ ] 定义统一的 `explain()` 方法签名
- [ ] 定义输入参数（样本、目标类别、解释方法等）
- [ ] 定义返回值格式

**验收标准**: 接口规范文档完成

### 子任务 2: 定义返回格式（JSON schema）
- [ ] 设计结构化解释 JSON 格式
  - `attribution`: 特征归因
  - `attention`: 注意力权重
  - `rules`: 规则激活（Fuzzy）
  - `path`: 决策路径（MoE）
- [ ] 编写 JSON schema 定义

**验收标准**: JSON schema 可被验证

### 子任务 3: 创建目录和基础代码
- [ ] 创建 `src/uxfd_api/` 目录
- [ ] 实现 `BaseExplainer` 抽象类
- [ ] 编写 API 文档

**验收标准**: 目录存在，基础代码可导入

---

## 选项

### 选项 A: 最小接口 + 扩展（推荐 ★）
- **描述**: 定义最小必需字段，扩展字段可选
- **优点**: 兼容性好，各模型可自定义扩展
- **缺点**: 需要处理扩展字段

### 选项 B: 完整接口
- **描述**: 定义所有可能的字段
- **优点**: 规范统一
- **缺点**: 部分模型可能无法提供某些字段
